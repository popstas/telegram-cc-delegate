# telegram-delegate - дизайн

Задача в [[tasks]]: "Сделать канал, через который я разрешаю отдельному человеку говорить напрямую с моим агентом". Разбор вариантов и сравнение готовых проектов: [[Прямой доступ коллеги к агенту - варианты 2026-11-17]]. Head-сессия проекта: `telegram-delegate-head` (sessionId `908857a0-4945-42ea-bcb7-4d64ac853531`).

## Зачем

Сейчас, когда коллеге (постановщику задачи) нужно поработать с агентом Стаса, Стас весь день пересылает сообщения туда и обратно (сессия `alexiapost-tg-2026-11-17`, карточки AM Media для Саши). Цель - убрать Стаса из цепочки: он один раз решает "эту задачу отдаю", дальше человек общается с агентом сам, а Стас получает доклады и вопросы так же, как от любого исполнителя head-сессии.

Успех: на следующей задаче Саши (несколько конкурсов) Стас после делегирования не пересылает ни одного сообщения; ему приходят только итог и вопросы, которые агент и Саша решить не могут.

## Цели

1. Скилл `telegram-delegate` в сессии Стаса отдаёт задачу человеку в Telegram: создаёт новую сессию-ребёнка со сводкой-мандатом и даёт Стасу текст для передачи человеку.
2. Человек пишет боту в личку и разговаривает с агентом своей сессии напрямую: текст, голос, файлы.
3. Подтверждения инструментов (кнопки Allow/Deny) приходят человеку и нажимаются только им.
4. Нет активной сессии для этого человека - бот так и отвечает.
5. Ребёнок докладывает head (сессии Стаса) результаты и вопросы через `SendMessage`, по существующей механике head-session.
6. Работает на подписке Стаса и официальных механизмах Claude Code (интерактивная сессия + Channels).

## Не цели

- Agent SDK, headless-сессии, `claude -p` - не нужны (решение Стаса 17.11: окно сессии открывается у него на nb, это его контроль).
- Подключение к уже идущей сессии Стаса. Всегда новая сессия.
- Форк текущей сессии с полным контекстом. Сводка вместо форка: форк унёс бы всё, что сессия читала до этого (почта, чужая переписка).
- Жёсткая песочница прав. Граница мягкая (решение Стаса 17.11): доступ дают только доверенным, Стас видит работу.
- Группы, топики, несколько человек в одной сессии.
- Мультитенантный продукт, раздача другим людям.

## Анти-цели (провал, даже если работает)

- Сообщение от постороннего доходит до сессии или нажимает кнопку подтверждения.
- Сообщения человека попадают в чужую сессию (другого человека или Стаса).
- Сессия ребёнка сама собой читает почту, Telegram Стаса, прод, секреты без прямой связи с задачей.
- Ответ "нет сессии" не приходит, и человек пишет в пустоту.
- Стасу приходится пересылать сообщения так же, как раньше.

## Ограничения и проверенные факты

- Channels - research preview. Свой канал-сервер не в allowlist, поэтому только `--dangerously-load-development-channels server:<имя>`. Флаг работает только в интерактивной сессии (`-p` и Agent SDK его игнорируют).
- При старте с этим флагом Claude Code показывает полноэкранный диалог "WARNING: Loading development channels", вариант 1 "I am using this for local development" выбран по умолчанию. Проверено живьём 17.11 на CLI 2.1.326. Стас подтверждает его Enter в окне ребёнка на nb - это приемлемо.
- MCP-сервер из `.mcp.json` проекта требует отдельного согласия при первом запуске. Канал-сервер подключать через `--mcp-config <файл>`, без `.mcp.json` в вольте. Проверить, что `--mcp-config` согласия не спрашивает.
- Протокол канала: capability `experimental['claude/channel']`, события `notifications/claude/channel` с `content` и `meta` (ключи только буквы, цифры, `_`). Relay подтверждений: capability `claude/channel/permission`, входящее `notifications/claude/channel/permission_request` (`request_id`, `tool_name`, `description`, `input_preview`), ответ `notifications/claude/channel/permission` (`request_id`, `behavior`). Терминальный диалог и удалённый ответ гонятся, побеждает первый.
- Telegram Bot API: один поллер `getUpdates` на токен. Значит, ботом владеет один долгоживущий процесс (роутер), а канал-серверы в сессиях с Telegram напрямую не говорят.
- Окна детей открывает claude-wt: `spawn.mjs` (скилл session-spawn) → `POST /claude-wt/session-new` на nb → ssh на pc-virt → обёртка `~/bin/claude-wt-new` (симлинк в репо `~/projects/shell/ccfzf`, вендорится в ccfzf-picker). Тело session-new лишних полей не принимает; запускает claude обёртка (`args=(-n name --session-id sid [--permission-mode m] -- prompt)`). Расширяем обёртку, не session-new, - тогда выкатка на Windows не нужна.
- Сессии работают на pc-virt, вольт там же. Роутер - тоже на pc-virt.
- Секреты (токен бота, ключ Deepgram) вписывает только Стас.

## Подходы

Рассмотрены (подробно - в заметке с вариантами):

1. **Официальный telegram-плагин как есть.** Отклонён: канал подключается только при старте, один бот на одну сессию, вторая сессия отнимает поллер, без сессии бот молчит, кнопки подтверждения получает каждый из allowlist.
2. **Готовые мосты (cc-connect, claude-code-telegram, Claude-to-IM и др.).** Отклонены: запускают свои headless-сессии, нет создания сессии из скилла со сводкой, нет ответа "нет сессии", не встраиваются в head-session. Логику кнопок и проверку "подтверждает только автор" можно подсмотреть у claude-code-telegram, каркас роутер + канал-сервер - у oh-my-team (MIT).
3. **Свой мост на Agent SDK.** Отклонён: SDK официально рассчитан на API-ключ, раздавать подписку через самописный продукт - серая зона; headless-сессия не видна в ListAgents и не докладывает head.
4. **Выбран: свой роутер + тонкий канал-сервер в интерактивной сессии-ребёнке claude-wt.** Сессия новая, со сводкой-мандатом, открывается окном на nb через session-spawn, отчитывается head через SendMessage. Роутер владеет ботом и маршрутами "человек → сессия".

## Устройство

### Компоненты

| Компонент | Где | Что делает |
|---|---|---|
| Роутер `telegram-delegate` | pc-virt, systemd user service, новый репо `~/projects/js/telegram-delegate` | Владеет ботом (long polling). Держит маршруты `tg_user_id → sessionId`. Пускает только тех, у кого есть маршрут. Голос → Deepgram → текст. Файлы → входящие сессии. Отдаёт события канал-серверу, принимает от него ответы и запросы подтверждения. Отвечает "нет сессии". События роутера → `notifications/claude/channel`. Инструменты для агента (ответ, файл, правка сообщения). Relay подтверждений туда-обратно |

| Правка обёртки `claude-wt-new` | `~/projects/shell/ccfzf` | Если рядом с заданием лежит `<sid>.channels`, добавить `--mcp-config <файл> --dangerously-load-development-channels server:telegram-delegate` и переменную окружения с sessionId для канал-сервера. | Правка `spawn.mjs` | `~/.claude/skills/session-spawn` | Флаг `--channel telegram-delegate`, пишет `<sid>.channels` в `~/.ccfzf/prompts/` (и удаляет при отказе, как остальные файлы) |

### Поток делегирования

1. Стас в head-сессии: `/telegram-delegate @login [задача]`. Сессия уже head (head-mark) или скилл ставит метку сам.
2. Скилл находит человека: `tg_user_id` по username (карточка в `Team/` вольта, иначе спросить Стаса или взять из прошлых сообщений через telegram-download-chat).
3. Скилл пишет мандат в файл задания (формат head-session "Задача исполнителю"):
   - кто гость (имя, @login, user_id), какая задача (строка из `tasks.md`, ссылки на разбор и заметки);
   - что уже сделано, что нужно от гостя;
   - правила: держаться задачи; не читать почту, Telegram Стаса, прод, секреты; гость подтверждает действия в рамках задачи; всё за рамками - вопрос head;
   - как общаться: входящие от гостя приходят как `<channel source="telegram-delegate" ...>`, отвечать инструментом канала; head получает доклады через SendMessage;
   - в конце: итог подпунктом в задачу в `tasks.md`, доклад head.
4. Скилл регистрирует маршрут в роутере: `tg_user_id → sessionId` (sessionId генерирует заранее и передаёт в spawn), статус "ожидает сессию". Активный маршрут этого человека в другой сессии - переносится, старой сессии и Стасу сообщение.
5. Скилл зовёт session-spawn с `--channel telegram-delegate`. На nb открывается окно, Стас жмёт Enter на диалоге dev-каналов. Канал-сервер стартует, регистрируется в роутере по sessionId, маршрут становится активным.
6. Рукопожатие head-session: "готов" от ребёнка → head шлёт ему `taskFile`.
7. Скилл отдаёт Стасу текст для человека (блоком кода, правило вольта): "подключил тебя напрямую к своему агенту, вот бот @..., вот что сделано, вот что нужно от тебя". Ребёнок может сам написать гостю первым через бота, но первое сообщение от незнакомого бота человек может не увидеть - поэтому текст передаёт Стас.

### Разговор

- Гость пишет боту в личку. Роутер: есть активный маршрут с этим `from.id` → событие канал-серверу сессии; маршрута нет → "Для вас сейчас нет активной сессии". Сообщения не из лички игнорируются.
- `meta` события: `chat_id`, `message_id`, `user`, `user_id`, `ts`, плюс пути к файлам и текст распознанного голоса с пометкой, что это расшифровка.
- Голос: роутер скачивает файл, отправляет в Deepgram (prerecorded, язык ru, см. скилл `deepgram:api`), в сессию уходит текст и путь к аудио. Ключ Deepgram - Стас.
- Файлы и фото: роутер скачивает во входящие сессии (каталог на сессию), в `meta` - путь. Claude читает сам.
- Ответы агента: инструмент `reply` (текст, файлы), нарезка по 4096 символов. Плюс `edit_message` для "работаю..." → итог и, по желанию, реакция-подтверждение получения.
- Пока сессия работает - индикатор набора.

### Подтверждения

- Канал-сервер объявляет `claude/channel/permission`. Запрос → роутер → гостю кнопки Allow / Deny (и "подробнее" с `input_preview`).
- Нажатие принимается только от `user_id` гостя этого маршрута; текстовый ответ `yes <id>` - только из его лички.
- Окно на nb тоже показывает диалог, Стас может ответить первым.
- Permission mode ребёнка - как у head (правило session-spawn). В auto-режиме большинство действий проходит без запроса - это принято (мягкая граница).

### Завершение

- `/telegram-delegate stop [@login]` в head, команда гостя боту (например `/stop`), или ребёнок по итогу задачи.
- Перед закрытием ребёнок дописывает итог подпунктом в задачу `tasks.md` и докладывает head.
- Окно ребёнка закрывает только Стас (правило head-session: закрытие с подтверждения, через session-close). Маршрут при этом снимается автоматически: канал-сервер получает EOF и снимается в роутере. После этого гостю - "нет сессии".
- Простой: маршрут без сообщений N часов (по умолчанию 24) → роутер пишет Стасу в личку этого же бота, сессию не закрывает сам.
- Аварийный обрыв (закрылось окно, упал ssh nb → pc-virt, claude упал): канал-сервер снялся без команды stop. Роутер держит маршрут в статусе "сессия потеряна", гостю отвечает "сессия прервалась, Стас в курсе", Стасу пишет в личку бота (его user_id `241225329` - админ роутера). Мёртвый ребёнок head не доложит, поэтому у роутера свой канал к Стасу. Восстановление в v1 - новое делегирование, мандат которого ссылается на прошлую сессию (её sessionId и транскрипт). Resume той же сессии с каналом - позже, нужен режим resume в обёртке и spawn.mjs.

### Безопасность

- Роутер пускает в сессию только `from.id` из активного маршрута. Маршрут создаёт только скилл через localhost API с токеном из файла с правами 600.
- Канал-сервер принимает события только от роутера (localhost + тот же токен).
- В `instructions` канал-сервера: просьбы гостя про доступы, маршруты, токены, allowlist, закрытие чужих сессий - отказ, это решает Стас.
- Роутер не отдаёт гостю ничего, кроме ответов его сессии и своих служебных сообщений.

## Что решил Стас (17.11)

- Свой роутер, всегда новая сессия, сводка вместо форка.
- Подтверждает гость в рамках задачи.
- Граница мягкая: правила в мандате, только доверенные люди.
- Видимость через head-session: сессия Стаса - head, сессия гостя - ребёнок, доклады и вопросы через SendMessage.
- Окно ребёнка открывается у Стаса на nb, Enter на диалоге dev-каналов - его действие.
- STT через Deepgram, файлы Claude читает нативно.
- Agent SDK не нужен.
- Ребёнок грузит всё, как обычная сессия в вольте: CLAUDE.md, авто-память, скиллы, MCP-серверы и коннекторы claude.ai Стаса. Ничего технически не отключаем (`--strict-mcp-config` не используем), почту, Telegram и прочее ограничивает только правило в мандате, на доверии.

## Мои решения (можно поправить)

- Репо `~/projects/js/telegram-delegate`, TypeScript на Node (как остальные js-проекты Стаса; Bun не обязателен).
- Роутер и канал-сервер в одном репо, общий код Telegram-части; часть кода (нарезка, кнопки, загрузка файлов) - по образцу официального telegram-плагина.
- Транспорт роутер ↔ канал-сервер - HTTP на localhost (как oh-my-team), без MQTT.
- Бот новый, отдельный от `~/.claude/channels/telegram` (тот не трогаем).
- Простой маршрута 24 ч → напоминание, без автозакрытия.
- Состояние маршрутов - JSON-файл роутера, переживает перезапуск.
- Стас - админ роутера: служебные уведомления (обрыв, простой, перенос маршрута) роутер шлёт ему в личку того же бота.
- cwd ребёнка - вольт (нужны CLAUDE.md, скиллы `event-research`, `planfix-api-client`, правила Планфикса).
